Convenciones del documento

Las palabras clave DEBE, NO DEBE, DEBERÍA, NO DEBERÍA y PUEDE se interpretan conforme a la práctica establecida en BCP 14 (RFC 2119 y RFC 8174):

TérminoSignificado normativo en este documento
DEBE / NO DEBERequisito absoluto. Su incumplimiento bloquea la aprobación de una entrega (véase la Definición de Terminado, §27.4).
DEBERÍARecomendación fuerte. Puede omitirse sólo con justificación registrada como decisión de arquitectura (apéndice H).
PUEDEOpción legítima; ninguna alternativa es preferente.

Las referencias cruzadas internas usan el signo § seguido del número de sección (por ejemplo, §11.4). Las fuentes externas se citan de forma abreviada en el cuerpo del texto —por ejemplo (W3C, WCAG 2.2, 2.5.8)— y se desarrollan con dirección completa en el apéndice J, «Bibliografía y fuentes consultadas». Los identificadores de requisito siguen el formato RQ-<dominio>-<número>; los de componente, CMP-<familia>-<nombre>; los de decisión de arquitectura, ADR-<número>. El código fuente de ejemplo se presenta en TypeScript y CSS; los fragmentos son ilustrativos de la especificación y no sustituyen al repositorio.

Nota terminológica

El documento emplea maestro–detalle (en inglés master–detail o list–detail) para designar el patrón de interfaz en el que un panel de selección gobierna el contenido de un panel dependiente. Se evita el par maestro/esclavo en la descripción de componentes de software y réplicas de datos, siguiendo las recomendaciones de lenguaje inclusivo adoptadas por la IETF y por las comunidades de Linux, Python y Redis, que prefieren pares como primario/réplica o primario/secundario; cuando el término heredado es imprescindible para localizar literatura previa, se indica entre paréntesis. El capítulo 11 trata explícitamente esta equivalencia terminológica.
