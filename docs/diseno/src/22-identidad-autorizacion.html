Capítulo 22Identidad, sesión y autorización

Este es el capítulo del que depende la integridad del producto. Especifica cómo se autentica a las personas, cómo se custodia la sesión, cómo se modelan los roles y —sobre todo— cómo se expresan las reglas de autorización en el único lugar donde son efectivas: el servidor. Incluye la sustitución completa de las reglas vigentes, que constituyen la deuda de seguridad más grave identificada en el diagnóstico.

22.1 Modelo de identidad

La autenticación se delega en un proveedor de identidad federado. El producto no almacena contraseñas, no implementa recuperación de cuenta y no gestiona segundo factor: hereda lo que el proveedor ofrezca. A cambio asume dos obligaciones: validar el testigo en cada operación de servidor —cosa que hace el motor de reglas— y no construir ninguna autorización sobre atributos del perfil que la persona pueda modificar.

Hallazgo H1 — la regla a eliminar

Las reglas vigentes conceden permisos de administración comparando request.auth.token.email con una dirección literal. Tres defectos: el correo electrónico es un atributo del perfil y no una autorización; la regla no admite delegación —si esa persona no está disponible, el torneo se bloquea—; y el privilegio no deja rastro de concesión ni de revocación. Su sustitución por roles con alcance de torneo es el requisito bloqueante RQ-AUT-04.

22.2 Flujo de autenticación y custodia de la sesión

  1. La persona inicia sesión mediante el proveedor federado en ventana emergente o redirección; el producto nunca ve credenciales.
  2. El proveedor devuelve un testigo de identidad de vida corta, que la biblioteca cliente renueva de forma transparente mientras la sesión siga siendo válida.
  3. Cada operación contra la base de datos envía ese testigo; el motor de reglas lo valida y expone su contenido verificado a las reglas.
  4. El cierre de sesión revoca localmente el estado, purga cachés, cola de escrituras y preferencias ligadas a la identidad, y cancela suscripciones en tiempo real.
  5. La sesión caduca por inactividad prolongada; antes de caducar se avisa con posibilidad de prolongarla, sin perder el trabajo en curso (criterio 2.2.1).

Las prácticas actuales de seguridad para clientes públicos exigen, cuando se implementa el flujo directamente: código de autorización con prueba de clave (PKCE) obligatorio, prohibición del flujo implícito, verificación estricta de los destinos de redirección y defensa frente a confusión de servidores de autorización. En este producto el flujo lo implementa la biblioteca del proveedor, pero la obligación permanece: si alguna vez se sustituye por una implementación propia, debe cumplir esas condiciones.

22.3 Autenticación accesible

El criterio 3.3.8 prohíbe exigir pruebas cognitivas —recordar, transcribir, resolver acertijos— sin alternativa. La identidad federada lo cumple de forma natural. Las obligaciones derivadas para el producto son: permitir el pegado en cualquier campo relacionado con el acceso, incluido el código de invitación; no imponer temporizadores cortos en la pantalla de acceso; no usar imágenes de verificación; y mantener el botón de acceso con nombre accesible explícito que nombre el proveedor, no un icono sin texto.

La decisión de almacenar la organización en el documento de torneo —y no como reclamación en el testigo— responde a tres razones: el rol es por torneo y no global; cambia con frecuencia y las reclamaciones se propagan con retardo hasta la renovación del testigo; y queda consultable y auditable por el grupo. El coste es una lectura adicional por evaluación de regla, asumible dado el volumen (ADR-05, apéndice H).

22.5 Incorporación segura a un torneo

La regla vigente permite a cualquier persona autenticada escribir el arreglo completo de participantes mientras el torneo esté en borrador. Eso autoriza, literalmente, a eliminar a los demás (hallazgo H3). Con el modelo de subcolección de §16.1 la operación se reduce a su mínimo legítimo: crear un documento cuyo identificador es la propia identidad, y sólo si el torneo está en borrador, el código aportado coincide y no se ha superado el límite de participantes. Nada más.

22.6 Reglas de autorización

Las reglas siguientes sustituyen íntegramente a las vigentes. Están escritas para ser legibles y verificables: funciones con nombre de dominio, denegación por defecto y validación de forma además de autorización.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // ---------- funciones de apoyo ----------
    function autenticado()      { return request.auth != null; }
    function yo()               { return request.auth.uid; }
    function esPlataforma()     { return autenticado() && request.auth.token.plataforma == true; }
    function torneo(id)         { return get(/databases/$(database)/documents/tournaments/$(id)).data; }
    function esOrganizador(id)  { return autenticado() && yo() in torneo(id).organizadores; }
    function esParticipante(id) {
      return autenticado() &&
        exists(/databases/$(database)/documents/tournaments/$(id)/players/$(yo()));
    }
    function puedeVer(id)       { return esParticipante(id) || esOrganizador(id) || esPlataforma(); }
    function soloCampos(permitidos) {
      return request.resource.data.diff(resource.data).affectedKeys().hasOnly(permitidos);
    }
    function selloValido() { return request.resource.data.actualizadoEn == request.time; }

    // ---------- perfiles ----------
    match /users/{uid} {
      allow get: if autenticado();
      allow list: if false;                         // no se enumera el directorio de personas
      allow create, update: if yo() == uid
        && request.resource.data.keys().hasOnly(['nombre','foto','actualizadoEn'])
        && request.resource.data.nombre is string
        && request.resource.data.nombre.size() >= 1
        && request.resource.data.nombre.size() <= 40
        && selloValido();
      allow delete: if yo() == uid;                 // derecho de supresión (§23.5)
    }

    // ---------- torneos ----------
    match /tournaments/{id} {
      allow get, list: if puedeVer(id);
      allow create: if autenticado()
        && request.resource.data.organizadores == [yo()]
        && request.resource.data.estado == 'borrador'
        && request.resource.data.nombre is string
        && request.resource.data.nombre.size() <= 60
        && request.resource.data.formato in ['liga','ligaIdaVuelta','gruposEliminatoria','eliminatoria'];
      allow update: if esOrganizador(id)
        && request.resource.data.estado in ['borrador','activo','eliminatoria','cerrado']
        && resource.data.estado != 'cerrado'      // un torneo cerrado es inmutable
        && selloValido();
      allow delete: if esOrganizador(id) && resource.data.estado == 'borrador';

      // ---------- participación ----------
      match /players/{uid} {
        allow get, list: if puedeVer(id);
        allow create: if autenticado() && uid == yo()
          && torneo(id).estado == 'borrador'
          && request.resource.data.codigo == torneo(id).codigoInvitacion
          && torneo(id).numeroParticipantes < torneo(id).maxParticipantes;
        allow delete: if (uid == yo() && torneo(id).estado == 'borrador') || esOrganizador(id);
        allow update: if esOrganizador(id) && soloCampos(['equipoId','grupo','orden']);
      }

      // ---------- partidos ----------
      match /matches/{mid} {
        allow get, list: if puedeVer(id);
        allow create, delete: if esOrganizador(id) && torneo(id).estado != 'cerrado';
        allow update: if esOrganizador(id)
          && torneo(id).estado != 'cerrado'
          && soloCampos(['golesLocal','golesVisitante','estado','registradoPor','registradoEn','idOperacion'])
          && request.resource.data.golesLocal is int
          && request.resource.data.golesLocal >= 0 && request.resource.data.golesLocal <= 99
          && request.resource.data.golesVisitante is int
          && request.resource.data.golesVisitante >= 0 && request.resource.data.golesVisitante <= 99
          && request.resource.data.registradoPor == yo()
          && request.resource.data.registradoEn == request.time;
      }

      // ---------- auditoría: sólo se añade, nunca se altera ----------
      match /auditoria/{entradaId} {
        allow get, list: if puedeVer(id);
        allow create: if esOrganizador(id) && request.resource.data.autor == yo();
        allow update, delete: if false;
      }

      // ---------- proyección derivada: sólo servidor ----------
      match /standings/{docId} {
        allow get, list: if puedeVer(id);
        allow write: if false;        // escrita exclusivamente por función con privilegios
      }
    }

    // ---------- catálogo y palmarés ----------
    match /teams/{teamId}  { allow get, list: if autenticado(); allow write: if esPlataforma(); }
    match /palmares/{uid}  { allow get, list: if autenticado(); allow write: if false; }

    // ---------- denegación por defecto ----------
    match /{document=**} { allow read, write: if false; }
  }
}

22.7 Verificación de las reglas

Las reglas se prueban con el emulador en una suite que, para cada operación, comprueba el caso permitido y el denegado. La cobertura mínima exigida es: cada allow con al menos una prueba positiva y una negativa por cada condición que lo compone. Las pruebas se ejecutan en integración continua y bloquean la publicación. Una regla sin prueba negativa no demuestra nada: lo que hay que demostrar es que lo prohibido se rechaza.

test('un participante no puede editar el marcador', async () => {
  const ctx = entornoPrueba.authenticatedContext('luis');
  await assertFails(
    ctx.firestore().doc('tournaments/t1/matches/m1').update({ golesLocal: 9, golesVisitante: 0 })
  );
});
test('la clasificación no es escribible por ningún cliente', async () => {
  const ctx = entornoPrueba.authenticatedContext('organizadora');
  await assertFails(ctx.firestore().doc('tournaments/t1/standings/actual').set({ filas: [] }));
});

22.8 Detección y respuesta

Se registran y alertan: denegaciones de reglas por encima de un umbral por identidad y hora —indicio de exploración—; escrituras de marcador fuera de la ventana temporal del torneo; cambios en el arreglo de organizadores; y consumo anómalo de lecturas. La protección de la aplicación frente a clientes no legítimos se refuerza con verificación de integridad de la aplicación en el acceso a la base de datos, de modo que un testigo robado desde un entorno distinto al cliente oficial sea rechazado.

22.9 Síntesis de requisitos del capítulo

  • RQ-AUT-01. Toda escritura DEBE autorizarse en servidor conforme a la tabla 1.3.
  • RQ-AUT-02. Las reglas DEBEN denegar por defecto y validar forma y rango además de identidad.
  • RQ-AUT-03. La lectura DEBE restringirse a quienes participan u organizan el torneo.
  • RQ-AUT-04. La autorización por dirección de correo literal DEBE eliminarse antes de cualquier ampliación funcional.
  • RQ-AUT-05. Cada regla DEBE tener prueba positiva y negativa automatizadas.
  • RQ-AUT-06. Los documentos derivados NO DEBEN ser escribibles por ningún cliente.
  • RQ-AUT-07. Un torneo cerrado DEBE ser inmutable salvo reapertura explícita y auditada.
