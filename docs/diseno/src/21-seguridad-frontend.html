Capítulo 21Seguridad del cliente web

El cliente no puede autorizar, pero sí puede ser el vehículo de un ataque contra quien lo usa. Este capítulo especifica los controles que reducen la superficie del navegador: prevención de ejecución de código inyectado, política de seguridad de contenido, cabeceras de respuesta, custodia de datos en el dispositivo, protección frente a encuadre y redirección abierta, y política de terceros.

21.2 Ejecución de código inyectado

El motor de interfaz escapa por defecto el texto que interpola, lo que elimina la clase más común de inyección. Las excepciones son explícitas y por eso peligrosas:

  • Inserción directa de HTML. Prohibida. Si alguna vez fuera imprescindible, exigiría saneamiento con biblioteca especializada, lista blanca estricta y revisión de seguridad registrada.
  • Atributos de URL. Un enlace cuyo destino proceda de datos debe validarse: sólo se admiten esquemas https: y rutas relativas. Un javascript: en un href ejecuta código.
  • SVG de origen externo. Prohibido: un SVG es un documento con capacidad de ejecución. Los iconos propios se empaquetan; los escudos remotos se sirven como imágenes rasterizadas.
  • Evaluación dinámica. Prohibidas las funciones que evalúan cadenas como código, directa o indirectamente.
  • Interpolación en estilos. Los valores de usuario nunca se concatenan en propiedades personalizadas que acaben en una función de obtención de recursos.

Como red de seguridad se activan Trusted Types, que convierten en error cualquier asignación de cadena a un punto de inyección del DOM salvo que pase por una política declarada. Esto protege también frente a dependencias de terceros que hagan lo que el código propio tiene prohibido.

// seguridad/politicaTiposConfiables.ts
if (window.trustedTypes?.createPolicy) {
  window.trustedTypes.createPolicy('default', {
    createHTML: () => { throw new Error('Inserción de HTML no permitida'); },
    createScriptURL: (url) => {
      const u = new URL(url, location.origin);
      if (u.origin !== location.origin) throw new Error('Script externo bloqueado: ' + u.origin);
      return url;
    },
    createScript: () => { throw new Error('Script dinámico no permitido'); },
  });
}

21.3 Política de seguridad de contenido y cabeceras

La aplicación se sirve como contenido estático; la política se inyecta en el borde, lo que permite emitir un nonce distinto por respuesta. Con strict-dynamic, los scripts cargados por un script de confianza heredan la confianza, de modo que la división de código funciona sin listar cada fragmento.

Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-{ALEATORIO}' 'strict-dynamic' https: 'unsafe-inline';
  style-src 'self' 'nonce-{ALEATORIO}';
  img-src 'self' data: https://lh3.googleusercontent.com;
  font-src 'self';
  connect-src 'self' https://*.googleapis.com https://*.firebaseio.com wss://*.firebaseio.com;
  frame-ancestors 'none';
  base-uri 'none';
  form-action 'self';
  object-src 'none';
  require-trusted-types-for 'script';
  trusted-types default;
  upgrade-insecure-requests;
  report-to csp-endpoint

'unsafe-inline' figura únicamente como alternativa para navegadores antiguos que no entienden nonce; los que sí lo entienden lo ignoran. Esa combinación es la recomendada para políticas estrictas compatibles.

21.5 Encuadre, redirección y enlaces

  • Encuadre. frame-ancestors 'none' impide incrustar la aplicación en otro sitio, cerrando los ataques de superposición de interfaz.
  • Redirección abierta. El parámetro destino se valida contra la lista de rutas conocidas (tabla 9.1); cualquier valor absoluto o desconocido se sustituye por la raíz. Sin esa validación, el enlace de inicio de sesión del producto sirve para enviar a cualquier sitio con apariencia de confianza.
  • Enlaces salientes. rel="noopener noreferrer" y target="_blank" sólo cuando esté justificado.
  • Mensajería entre ventanas. No se usa; si la ventana emergente de identidad la emplea, la gestiona íntegramente la biblioteca del proveedor y el producto no escucha mensajes propios.

21.6 Validación de entrada y gestión de condiciones excepcionales

Toda entrada se valida en tres puntos: el control la restringe (ergonomía), el cliente la comprueba antes de enviar (ergonomía) y el servidor la rechaza si no cumple (seguridad). Las reglas de validación son parte del contrato de datos (§16.2) y no pueden relajarse en el cliente «para probar».

La gestión de condiciones excepcionales merece mención propia porque es una categoría de riesgo por derecho propio: ante error de red, respuesta inesperada o regla que no se puede evaluar, el comportamiento especificado es denegar y comunicar, nunca continuar asumiendo éxito. Los mensajes mostrados no revelan detalles internos —rutas, consultas, identificadores de infraestructura— y lo que se registra para diagnóstico no viaja al navegador (§23.6).

21.7 Terceros

Política: cero terceros en la ruta crítica. No se cargan fuentes, analítica, mapas, widgets ni etiquetas de márketing desde dominios ajenos. La única comunicación externa es con los servicios de la plataforma de datos e identidad, declarados explícitamente en connect-src. Si en el futuro se incorpora analítica, debe ser autoalojada o proxificada en el propio origen, sin cookies de terceros y con medición agregada sin perfilado individual. Cualquier excepción a esta política requiere decisión de arquitectura registrada y revisión de seguridad.

21.8 Síntesis de requisitos del capítulo

  • RQ-SEC-01. El despliegue DEBE emitir la política de contenido y el conjunto de cabeceras de la tabla 21.2.
  • RQ-SEC-02. La inserción directa de HTML y la evaluación dinámica de código están PROHIBIDAS; se verifica con análisis estático.
  • RQ-SEC-03. Trusted Types DEBE estar activo en modo de aplicación.
  • RQ-SEC-04. Ningún testigo de acceso DEBE almacenarse en almacenamiento accesible por script fuera de la gestión de la biblioteca de identidad.
  • RQ-SEC-05. Los parámetros de redirección DEBEN validarse contra lista de rutas conocidas.
  • RQ-SEC-06. Ante condición excepcional, el sistema DEBE denegar y comunicar, nunca continuar.
  • RQ-SEC-07. NO DEBEN cargarse recursos de terceros en la ruta crítica.
