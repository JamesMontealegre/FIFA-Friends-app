Capítulo 14Arquitectura de aplicación de página única

Una aplicación de página única traslada al navegador responsabilidades que tradicionalmente eran del servidor: enrutamiento, composición de vistas y gestión de estado. Ese traslado tiene ventajas reales y costes reales. Este capítulo explica por qué es la arquitectura adecuada para este producto, especifica el modelo de ejecución, el enrutamiento, la división de código y los límites de error, y documenta qué se pierde y cómo se compensa.

14.2 Modelo de ejecución

El modelo tiene tres propiedades que condicionan todo lo demás. Un solo hilo principal: cualquier cálculo largo bloquea la respuesta a la interacción y degrada directamente la métrica de capacidad de respuesta (§25.3). Un único documento: la navegación no recarga, luego el estado persiste pero también persisten las fugas, los temporizadores y las suscripciones no limpiadas. El código es público: todo lo que viaja al navegador es legible e inspeccionable, de modo que ninguna decisión de seguridad puede depender de él (§21.1).

14.3 Enrutamiento

El enrutador es declarativo y anidado: el armazón de la aplicación es una ruta padre que contiene las vistas, de modo que cambiar de vista no desmonta la cabecera ni la navegación. Las reglas:

  • Las rutas se declaran en un único módulo, que es la traducción literal de la tabla 9.1.
  • Cada ruta declara su componente perezoso, su límite de error y su respaldo de carga. Un fallo al cargar una vista no derriba la aplicación: muestra el error dentro del armazón, con la navegación intacta.
  • La protección de rutas se implementa como componente envolvente que decide entre contenido, redirección a inicio de sesión conservando el destino, o estado «sin permiso». Nunca es un control de seguridad: sólo evita mostrar interfaz inútil (§21.1).
  • Los parámetros de consulta se leen y escriben mediante una utilidad tipada que valida los valores y aplica los predeterminados, de modo que una URL manipulada nunca produzca estados imposibles.
const rutas = [
  { path: '/', element: <Armazon />, errorElement: <ErrorDeRuta />, children: [
    { index: true,            lazy: () => import('./vistas/Ahora') },
    { path: 'tournaments',    lazy: () => import('./vistas/Torneos') },
    { path: 'tournaments/new',lazy: () => import('./vistas/CrearTorneo'), handle: { rol: 'organizador' } },
    { path: 'tournaments/:id',lazy: () => import('./vistas/DetalleTorneo'), children: [
      { path: 'matches/:matchId', lazy: () => import('./vistas/DetallePartido') },
    ]},
    { path: '*', lazy: () => import('./vistas/NoEncontrada') },
  ]},

Tres reglas adicionales: no se divide por debajo de 15 KB, porque el coste de una petición adicional supera el ahorro; las dependencias compartidas por tres o más vistas se agrupan en un fragmento común para evitar duplicación; y la precarga por intención se cancela si la red declara modo de ahorro de datos.

14.5 Renderizado y reconciliación

  • Claves estables. Toda lista se identifica por el identificador del documento, nunca por el índice: con índices, insertar un partido al principio reordena el estado de todas las filas.
  • Memoización automática. El compilador de la biblioteca de interfaz introduce la memoización necesaria; no se añaden envoltorios manuales salvo que una medición demuestre su necesidad. Optimizar sin medir añade complejidad sin beneficio.
  • Estado al nivel más bajo posible. El estado que sólo afecta a un componente vive en él; elevarlo provoca repintados en cascada.
  • Listas largas. Virtualización sólo por encima de 150 elementos (§11.9).
  • Cálculos costosos. La generación de calendario y el cálculo de posiciones del cuadro se ejecutan fuera del hilo principal cuando superan 50 ms medidos, o se trocean con cesión explícita del hilo (§25.3).

14.7 Navegación percibida

La ventaja principal de esta arquitectura es la navegación sin recarga; perderla por esperar datos la anula. Reglas: la vista se muestra inmediatamente con los datos ya cacheados y revalida en segundo plano; una navegación nunca deja la pantalla en blanco más de 200 ms; las transiciones entre vistas usan la interfaz de transiciones del navegador cuando está disponible y se omiten silenciosamente cuando no; y la posición de desplazamiento se restaura al retroceder y se reinicia al avanzar, salvo en el patrón maestro–detalle, donde rige §11.7.

14.9 Síntesis de requisitos del capítulo

  • RQ-SPA-01. Cada ruta DEBE cargarse de forma perezosa y declarar su límite de error y su estado de carga.
  • RQ-SPA-02. El fragmento del armazón NO DEBE superar su presupuesto; el incumplimiento falla la construcción.
  • RQ-SPA-03. La protección de rutas NO DEBE considerarse control de seguridad.
  • RQ-SPA-04. Los parámetros de consulta DEBEN validarse y tener valores por defecto tolerantes.
  • RQ-SPA-05. Las listas DEBEN usar claves estables basadas en identidad de dominio.
  • RQ-SPA-06. La publicación de una versión nueva NO DEBE forzar recarga sin consentimiento.
