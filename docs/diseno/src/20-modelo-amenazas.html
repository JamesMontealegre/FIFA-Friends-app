Capítulo 20Modelo de amenazas y arquitectura de seguridad

La seguridad de una aplicación sin servidor propio se juega en dos sitios: en lo que el navegador permite ejecutar y en lo que la base de datos permite escribir. Este capítulo establece los límites de confianza, identifica los activos, aplica un análisis sistemático de amenazas y fija los principios y el nivel de verificación que gobiernan los tres capítulos siguientes.

20.1 Premisa

Premisa fundamental

Todo el código que se ejecuta en el navegador es público, legible y modificable por quien lo ejecuta. Las comprobaciones del cliente son ergonomía, no seguridad. Cualquier regla que importe —quién puede escribir qué, con qué valores y en qué estado— debe verificarse en un lugar que la persona usuaria no controle. En esta arquitectura ese lugar es el motor de reglas de la base de datos y las funciones de servidor.

20.3 Análisis sistemático de amenazas

Se aplica el esquema de categorías de amenaza —suplantación, manipulación, repudio, revelación de información, denegación de servicio y elevación de privilegios— a cada cruce de frontera.

SuplantaciónUsar la sesión de otra persona para registrar resultados.Identidad federada con testigo de corta vida y renovación; ninguna credencial en almacenamiento persistente accesible por script (§22.2).

20.5 Principios de seguridad adoptados

  1. Mínimo privilegio. Cada regla concede lo justo: campos concretos, estados concretos, identidades concretas.
  2. Denegación por defecto. Lo que no está explícitamente permitido, está prohibido. Las reglas terminan sin cláusula permisiva general.
  3. Defensa en profundidad. El cliente valida para ayudar; el servidor valida para proteger; la auditoría permite detectar lo que ambos dejen pasar.
  4. Fallo cerrado. Ante error, ausencia de datos o condición imprevista, se deniega. Es la respuesta directa a la categoría de condiciones excepcionales.
  5. Superficie mínima. Ninguna dependencia, ningún recurso de terceros y ningún permiso que no esté justificado por un requisito.
  6. Seguridad verificable. Cada regla relevante tiene una prueba automatizada que comprueba tanto el caso permitido como el denegado (§26.6).

20.6 Nivel de verificación objetivo

Se adopta como objetivo el nivel 2 del estándar de verificación de seguridad de aplicaciones, aplicado a los requisitos pertinentes para una aplicación sin servidor propio con autenticación delegada. Los requisitos relativos a gestión de contraseñas, criptografía propia o procesamiento de pagos no aplican y se declaran como tales —no como «cumplidos»—. La trazabilidad requisito a requisito está en el apéndice C, con los identificadores citados con versión completa para evitar ambigüedad entre ediciones del estándar.

20.7 Síntesis de requisitos del capítulo

  • RQ-SEG-01. Ninguna decisión de autorización DEBE depender de código ejecutado en el navegador.
  • RQ-SEG-02. Las reglas de servidor DEBEN denegar por defecto y fallar cerradas.
  • RQ-SEG-03. Cada amenaza de la tabla 20.2 DEBE tener un control implementado y verificable.
  • RQ-SEG-04. El modelo de amenazas DEBE revisarse ante cada cambio de arquitectura o de superficie de datos.
  • RQ-SEG-05. Los requisitos no aplicables del estándar de verificación DEBEN declararse como no aplicables, nunca como cumplidos.
