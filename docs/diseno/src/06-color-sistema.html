Capítulo 6Sistema de color del producto

Este capítulo convierte la teoría del capítulo anterior en valores concretos: una arquitectura de tokens en tres niveles, cinco familias cromáticas generadas en OKLCh con su contraste verificado, un mapa semántico para modo claro y modo oscuro, reglas de superficie y elevación, y el mecanismo de implementación y verificación automática que impide la deriva.

6.1 Arquitectura de tokens

Un sistema de color sostenible no expone colores: expone intenciones. Se definen tres niveles, y sólo el intermedio puede usarse al construir pantallas.

6.2 Nomenclatura

El nombre de un token semántico se compone como color-<rol>-<elemento>[-<estado>], donde el rol es la función (acción primaria, superficie, texto, borde, estado), el elemento indica qué parte se colorea (fondo, texto, borde, icono) y el estado es opcional (reposo implícito, hover, activo, foco, deshabilitado, seleccionado). Ejemplos válidos: color-superficie-elevada, color-texto-secundario, color-estado-error-borde, color-accion-primaria-fondo-hover. Los nombres nunca contienen el color («verde», «rojo») ni valores («claro-2»): un token llamado color-verde-boton impide cambiar la marca sin renombrar todo el sistema.

6.3 Paleta primitiva

Las cinco familias se generan algorítmicamente en OKLCh con once pasos de claridad decreciente y croma atenuado en los extremos para evitar que los tonos claros parezcan lavados y los oscuros, embarrados. Todos los valores están dentro de la gama sRGB; cuando el croma nominal excedía la gama, se redujo hasta el máximo representable conservando claridad y tono, de modo que la regularidad perceptual de la escala se mantiene. Las dos últimas columnas documentan el contraste verificado numéricamente y son la razón por la que cada paso tiene el uso asignado que tiene.

Lectura de las tablas

El paso 600 es el primero que alcanza 3:1 sobre blanco y por tanto el mínimo admisible para bordes de control, iconos informativos y gráficos. El paso 700 es el primero que supera 4,5:1 y por tanto el mínimo para texto normal sobre fondo claro. En modo oscuro la relación se invierte: los pasos 300 y 400 son los que ofrecen contraste suficiente sobre la tinta de fondo. Esta correspondencia —600 para componentes, 700 para texto, 300/400 en oscuro— es la regla mnemotécnica que el equipo debe memorizar.

6.5 Indicador de foco

El foco de teclado es el único mecanismo de orientación de quien no usa puntero, y es el elemento que más a menudo se destruye por motivos estéticos. La especificación es estricta:

  • Anillo de 2 px sólido en color-foco, con desplazamiento exterior de 2 px respecto al control, de modo que no reduzca el área táctil ni se confunda con el borde del propio control.
  • Contorno adicional de 1 px en color-superficie entre control y anillo: así el indicador sigue siendo visible tanto sobre fondos claros como oscuros, sin necesidad de dos tokens distintos.
  • Implementación con :focus-visible, nunca con :focus a secas, para no mostrar el anillo tras una pulsación con puntero.
  • outline: none sin sustituto equivalente está prohibido; la regla se verifica mediante análisis estático en integración continua (§26.4).
  • El anillo debe permanecer visible: ningún elemento fijo puede taparlo (criterio 2.4.11), lo que obliga a reservar espacio de desplazamiento adicional bajo las barras fijas (§10.4).
:where(a, button, input, select, textarea, summary, [tabindex]):focus-visible {
  outline: 2px solid var(--color-foco);
  outline-offset: 2px;
  border-radius: var(--radio-sm);
}
/* En modo de contraste forzado el sistema sustituye los colores:
   se usa la palabra clave del sistema para no perder el indicador. */
@media (forced-colors: active) {
  :where(a, button, input, select, textarea, summary, [tabindex]):focus-visible {
    outline: 3px solid Highlight;
  }
}

6.6 Modo oscuro

El modo oscuro no es una inversión: es un segundo mapa semántico sobre la misma paleta primitiva. Las reglas que lo gobiernan derivan de la fisiología descrita en §5.2:

  1. Nunca negro puro. El fondo es #0D1316 (una tinta derivada de neutro-950 con ligera componente del tono de marca). El negro absoluto sobre panel emisor maximiza el deslumbramiento del texto blanco y agrava el efecto de halo.
  2. Nunca blanco puro para texto largo. Se usa neutro-100, que reduce el deslumbramiento sin perder contraste (15,7:1 sobre la tinta).
  3. Reducir el croma de los acentos. Los colores saturados sobre fondo oscuro producen aberración cromática percibida; se usan los pasos 300 y 400, no 600 y 700.
  4. Elevar aclarando. Cada nivel de superficie aumenta la claridad entre 0,02 y 0,04 en OKLCh respecto al anterior.
  5. Respetar la preferencia del sistema y permitir anularla. Se implementa con prefers-color-scheme más un conmutador explícito de tres estados —claro, oscuro, automático— persistido por dispositivo.

6.8 Implementación

Los tokens se publican en el formato estable del módulo de tokens de diseño, y de ahí se generan las propiedades personalizadas de CSS y la configuración del motor de utilidades. El origen es único: ninguna herramienta define colores por su cuenta.

// tokens/color.json — formato DTCG (extracto)
{
  "color": {
    "cesped": {
      "700": { "$type": "color", "$value": "#087139",
               "$extensions": { "oklch": "oklch(0.482 0.1237 152)" } }
    },
    "accion": {
      "primaria": {
        "fondo":  { "$type": "color", "$value": "{color.cesped.700}" },
        "texto":  { "$type": "color", "$value": "#FFFFFF" }
      }
    }
  }
}
/* styles/tokens.css — generado, no editar a mano */
@theme {
  --color-cesped-700: oklch(0.482 0.1237 152);
  --color-neutro-900: oklch(0.306 0.0071 170);
  --color-accion-primaria-fondo: var(--color-cesped-700);
  --color-texto-principal: var(--color-neutro-900);
}
:root[data-tema="oscuro"], :root:not([data-tema="claro"]) {
  @media (prefers-color-scheme: dark) {
    --color-accion-primaria-fondo: var(--color-cesped-400);
    --color-texto-principal: var(--color-neutro-100);
  }
}
Transición entre temas

El cambio de tema NO DEBE animarse con transiciones de color sobre toda la página: produce un repintado costoso y resulta desagradable. Se aplica de forma instantánea, y se respeta prefers-reduced-motion en cualquier caso (§8.8).

6.9 Verificación automática

La deriva cromática se previene con una comprobación que se ejecuta en cada integración y falla la construcción si un par declarado incumple su umbral. La prueba recorre el mapa semántico, no las pantallas, lo que la hace barata y exhaustiva.

// scripts/verificar-contraste.ts (extracto)
const PARES: Array<[string, string, number]> = [
  ['color-texto-principal',   'color-superficie',            4.5],
  ['color-texto-secundario',  'color-superficie',            4.5],
  ['color-texto-terciario',   'color-superficie',            4.5],
  ['color-texto-inverso',     'color-accion-primaria-fondo', 4.5],
  ['color-borde-fuerte',      'color-superficie',            3.0],
  ['color-foco',              'color-superficie',            3.0],
  ['color-estado-error-texto','color-superficie',            4.5],
];
for (const modo of ['claro', 'oscuro'] as const) {
  for (const [frente, fondo, minimo] of PARES) {
    const r = contraste(resolver(frente, modo), resolver(fondo, modo));
    if (r < minimo) fallar(`${frente}/${fondo} en ${modo}: ${r.toFixed(2)} < ${minimo}`);
  }
}

6.10 Síntesis de requisitos del capítulo

  • RQ-COL-06. Ningún componente DEBE contener literales de color ni referencias a tokens primitivos.
  • RQ-COL-07. El modo oscuro DEBE implementarse como mapa semántico independiente, no como inversión ni como filtro.
  • RQ-COL-08. El indicador de foco DEBE cumplir la especificación de §6.5 en todos los controles, incluidos los personalizados.
  • RQ-COL-09. La verificación de contraste DEBE ejecutarse en integración continua y bloquear la construcción ante incumplimiento.
  • RQ-COL-10. El producto DEBE respetar prefers-color-scheme y ofrecer conmutador explícito de tres estados persistido.
